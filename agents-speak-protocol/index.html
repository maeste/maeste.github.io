history · part 1

Every revolution standardized how things talk

Before TCP/IP       → networks spoke dialects
Before HTTP         → every service invented its own wire format
Before REST         → SOAP was the only "enterprise" answer
Before WebSockets   → polling everywhere

Each time, entropy was reduced not by better applications, but by agreeing on how things connect.

⏱ min 2-4. Quattro righe, quattro epoche: non leggere le righe, raccontarle come un ritmo (chi era in azienda ai tempi di SOAP può confermare). Il punto non è la storia: è che l'entropia NON è stata ridotta da applicazioni migliori, ma da un accordo su come le cose si connettono. Land: "entropy was reduced by agreeing on how things connect".
history · part 2

History's rule

TCP/IP vs OSI · CORBA vs REST · SOAP vs JSON · WebSockets vs polling

Winners are rarely the most feature-rich.

The simplest protocol that reduces the most uncertainty wins.

⏱ min 4-5.5. Il precedente canonico da raccontare per bene: OSI era il protocollo completo, a strati, disegnato dai comitati; TCP/IP era semplice, specificato in RFC corte, e ship-pava. Ha vinto il più semplice, non il più completo: è lo stesso film di SOAP vs JSON (vince il più semplice) e WebSockets vs polling (vince chi cambia il modello di comunicazione, non chi aggiunge feature). CORBA vs REST solo nominata. QUESTA frase è la regola del talk: torna nella slide delle scommesse. Se il tempo stringe: solo OSI + la regola, 1 minuto.

boundary 1 · the model

Open Responses

  • De facto: Chat Completions semantics — the lingua franca spoken by clients, gateways, providers
  • Next: Responses API — typed items, semantic streaming events, state across turns (agent-native, not chat-shaped)
  • Open Responses: the same contract as an open spec — initiated by OpenAI, built with the OSS community (Hugging Face); an IETF draft for multi-provider inference uses it as reference
  • Already real: Vercel AI SDK ships an Open Responses provider
≈ POSIX for model APIs — one contract, many kernels, portable apps
emerging
⏱ min 8.5-11. Il momento POSIX: quando i dialetti vendor convergono su un contratto unico, le applicazioni diventano portabili (UNIX vendor → POSIX → software portabile; qui API vendor → Open Responses → agenti portabili). Chat Completions ha vinto come dialetto comune de facto; Responses è la generazione dopo: item tipati, eventi di streaming semantici, stato tra turni: un contratto pensato per agenti, non per chat. Segnali che non è vaporware: draft IETF che lo usa come riferimento, provider già dentro l'AI SDK di Vercel. Per il pubblico: se scrivete gateway o app multi-provider è il contratto da tenere d'occhio; se siete locked su un vendor, oggi non vi cambia la vita.
boundary 2 · tools

MCP

diagram: modelcontextprotocol.io
  • Official analogy: USB-C for AI applications — one port, any peripheral
  • JSON-RPC 2.0 over stdio or Streamable HTTP; host (owns model + user) → client (1:1) → server (capabilities)
  • Three primitives, three controllers: tools (model decides) · resources (app decides) · prompts (user decides)
  • The N×M integration problem becomes N+M: one adapter, every agent × every tool
  • Ecosystem is the moat: Claude, ChatGPT, VS Code, Cursor already speak it
  • Extensions: MCP Apps (sandboxed HTML), Skills over MCP (in development)
≈ JDBC/ODBC for the agent era — one driver API, any database behind it
de facto standard
⏱ min 11-15. Il diagramma ufficiale racconta da solo il problema N×M: a sinistra le AI application (chat, IDE), a destra dati e tool, in mezzo UN protocollo: gli adattatori si scrivono una volta. Per un ingegnere: è JDBC. L'app parla un driver API, dietro c'è qualsiasi database. I tre ruoli: l'host possiede modello e utente, il client vive nell'host (1:1 col server), il server espone capability. Il dettaglio che pochi notano e che distingue le primitive: CHI le controlla. Tools: decide il modello (function calling). Resources: decide l'applicazione (dati contestuali). Prompts: decide l'utente (template). Estensioni (MCP Apps, Skills over MCP): fuori dal supporto base, verificarle prima di dipendere. Quando usarlo: esporre i VOSTRI dati/tool a qualunque runtime agentico, o consumare capability esterne nel vostro agente.
boundary 3 · other agents

A2A

diagram: a2a-protocol.org (Linux Foundation)
  • The problem it kills: without a standard, every agent pair is a bespoke point-to-point integration (official scenario: a travel planner delegating to flight, hotel, currency agents)
  • Web-style discovery: Agent Card at /.well-known/ — capabilities, auth, endpoints, self-described
  • Lifecycle: Tasks (stateful, long-running) · SSE streaming + push notifications · results as Artifacts
  • Built on what exists: HTTP, JSON-RPC, SSE — design principle #1 is reusing the web's standards
  • Opaque execution: no model, tools or memory exposed — you negotiate with a peer, not inspect a tool
≈ Agent Card = OpenAPI for agents · Tasks = message-queue jobs (states, acks, retry)
1.0 stable
⏱ min 15-18. Lo scenario ufficiale: un agente di viaggio che compone agente voli, agente hotel, agente valuta. Senza standard: integrazioni point-to-point su misura, esattamente il mondo pre-API. Discovery alla web: l'Agent Card sta su /.well-known/ come robots.txt e security.txt, la controparte si descrive da sola (capability, auth, endpoint). Ciclo di vita: Task con stati (submitted, working, completed), streaming SSE per il progresso, push per il lungo periodo, risultati come Artifact. Per un ingegnere: i Task sono job da message queue, la Agent Card è l'OpenAPI della controparte. E il principio di design #1 del protocollo è riusare gli standard del web: HTTP, JSON-RPC, SSE, niente di esotico. Opaque execution: il remoto non espone nulla del proprio interno, negotiate come pari. Anticipa la slide dopo: è la differenza con MCP.
the concrete architecture

MCP and A2A in the same system

My agent
── MCP ──▶
My toolsMCP server · capability access
My agent
── A2A ──▶
Partner agentoutcome delegation
···▶
own model · own tools · own contextopaque execution

MCP: capability access — my agent calls your tools. A2A: outcome delegation — your agent keeps its stack private.

Why not wrap agents as tools? Agents are not tools — wrapping amputates negotiation, planning, asking back.

Rule of thumb: stateless capability → MCP · autonomous counterpart with its own state → A2A.

⏱ min 18-21.5. LA slide che l'abstract promette: architettura concreta, side by side. Nel diagramma: il nostro agente usa MCP per i SUOI tool, e A2A per delegare lavoro cross-org a un agente partner, che gira col suo stack e non espone nulla. La regola pratica da lasciare loro: capability senza stato → MCP; controparte autonoma col suo stato → A2A. E il motivo per cui non si avvolge un agente in un tool (dritto dai doc A2A, "agents are not tools"): un agente impacchettato come tool perde la capacità di negoziare, pianificare, fare domande indietro, diventa una funzione sorda. Esempio parlato: un agente di supporto interno che gestisce i tool aziendali via MCP e delega a un agente partner la parte che richiede dati che non possediamo. Complementari, non competitivi: come JDBC e REST in uno stesso backend.
boundary 4 · users

Three names, one boundary

diagram: docs.ag-ui.com (CopilotKit)
  • Why request/response dies here: runs are long-running with intermediate output, nondeterministic (the agent decides what to render next), mix structured + unstructured IO, need human-in-the-loop
  • AG-UI = typed event vocabulary (run lifecycle, messages, tool calls, STATE_SNAPSHOT/DELTA) over plain HTTP/SSE/WebSocket — transport- and framework-agnostic (LangGraph, CrewAI, ADK, Pydantic AI speak it)
  • Human-in-the-loop as a first-class event: pause for approval or credentials, resume later
  • A2UI = declarative UI: component descriptions from a client-owned catalogue → native widgets; the client never executes agent code
  • Composable: an A2UI payload rides over AG-UI or A2A · MCP Apps = same idea (sandboxed iframe) on the MCP side
≈ A2UI re-discovers HTML's contract: markup from the server, rendering owned by the client · AG-UI ≈ EventSource/MQTT: a standardized event stream
AG-UI: draft A2UI: 0.9.1
⏱ min 21.5-25. Il diagramma ufficiale mostra il punto: a sinistra il grafo dell'agente, a destra l'applicazione, in mezzo solo eventi tipati, e guardate il payload nel quadrante: STATE_SNAPSHOT con dentro lo stato sincronizzato, non testo. Perché serve un protocollo qui: il request/response presuppone una risposta finita e deterministica, un run agentico è lungo, produce output intermedio e nondeterministico (l'agente decide COSA mostrare dopo), mescola strutturato e testo, e a volte si ferma a chiedere. AG-UI porta ordine: un vocabolario di eventi standard su HTTP/SSE/WS, non un WebSocket su misura per app; i framework principali lo parlano già (LangGraph, CrewAI, ADK, Pydantic AI: i loghi nel diagramma). Human-in-the-loop come evento di prima classe: pausa per approvazione o credenziali, resume dopo: il pattern enterprise. A2UI: l'agente DESCRIVE, il client possiede il catalogo e renderizza widget nativi, mai codice arbitrario: è il contratto di HTML riscoperto (markup dal server, rendering del client). MCP Apps: la stessa idea lato MCP, iframe sandboxed.
boundary 5 · knowledge & instructions

Knowledge rides the filesystem

  • AGENTS.md: repo convention, narrows as you descend — ≈ robots.txt for repos
  • Agent Skills: a folder with SKILL.md + scripts and references; progressive disclosure (discover the name → load the instructions → execute) — ≈ man pages: synopsis always loaded, full page on demand
  • Agent Plugins: one package, plugin.json + skills/ + mcp.json; vendor-neutral interoperability floor; spec 1.0.0, TSC from Amazon, Cursor, Microsoft, OpenAI, Vercel — ≈ apt/homebrew packages
  • OpenTelemetry GenAI: one trace across model calls, tools, agents — ≈ the OTel you already run: new gen_ai.* conventions next to http.* and db.* — status Development
⏱ min 25-28. Ritmo da lista, ma ogni riga ha il suo cugino classico. AGENTS.md: convenzione pura, zero runtime, come robots.txt: funziona perché tutti la rispettano. Skills: la progressive disclosure è esattamente la filosofia delle man pages, nome e synopsis sempre in memoria, pagina completa solo quando serve; nata da Anthropic, ormai spec aperta con supporto ampio. Plugins: pacchetti alla apt/homebrew, manifest, skill e MCP server in un bundle; il punto per questo pubblico è l'interoperability floor (core portabile, il client tiene distribuzione e UX) e il TSC con cinque vendor pesanti: è il segnale a cui guardare. OTel GenAI: non imparate nulla di nuovo se usate già OTel, sono le semantic conventions gen_ai.* accanto a http.* e db.*; Development, pinnare la versione.
boundary 6 · the ide — kept short on purpose

ACP

  • JSON-RPC between code editor and coding agent: init, sessions, prompt/progress, permissions, cancel
  • v1 stable v2 experimental
  • The LSP parallel — and where it stops: agents are stateful and act with authority
⏱ min 28-29. Breve DI PROPOSITO, e dirlo: è il confine che si collega meno agli altri, vive nel mondo IDE. Il parallelo giusto è LSP: un contratto invece di N integrazioni editor-specifiche. Ma dove il parallelo si ferma: LSP risponde a domande, l'agente tiene sessioni di stato e agisce con autorità sul codebase (permissions, cancel). the newest boundary · payments

The boundary nobody used for 30 years

HTTP 402 "Payment Required": reserved in the protocol since 1996, never put to use.

The old world — 5 frictions
  • create account
  • KYC + payment method
  • buy credits
  • manage API keys
  • pay and reconcile
The x402 way — 3 steps
  • request
  • 402 + terms (scheme, asset, amount, payTo)
  • pay and retry with proof → 200

Keyless, per-call, machine-speed · zero protocol fees · blockchain-agnostic (EVM + Solana) · extensible to traditional rails · Linux Foundation project, audited, millions of transactions

≈ TLS made security a transport feature; x402 makes payment one — same shape as the 401 flow you know: challenge → retry, but the credential is money
production claims
⏱ min 29-31.5. La storia che chiude il cerchio: il protocollo aveva riservato un posto per i pagamenti trent'anni fa, gli agenti gli hanno dato un motivo per esistere. Le macchine non hanno carte di credito: il confronto è nelle due colonne. A sinistra il mondo che conoscete (account, KYC, crediti, API key, riconciliazione: cinque attriti prima che una macchina consumi un'API), a destra tre passi: richiesta, 402 con i termini (scheme, asset, amount, payTo), pagamento e retry con proof. La forma è quella del 401 che conoscete: challenge → retry con credenziali, solo che la credenziale è denaro. E come TLS ha reso la sicurezza una feature del transport, x402 fa lo stesso col pagamento: non è un gateway, è nel protocollo. Zero fee di protocollo, agnostico (EVM e Solana, estensibile a rail tradizionali: se esce la domanda crypto, questa è la risposta). Progetto Linux Foundation, audited, milioni di transazioni in produzione; status onesto: adozione da dimostrare. Il flusso completo disegnato sta in appendice.

takeaways

Three sentences to take home

1 · Standards arrive one boundary at a time, not as a platform.

2 · Complement, don't compete: MCP and A2A side by side, each doing what it does best.

3 · Adopt where the pain is — the simplest protocol that reduces the most uncertainty wins.

appendix A3 · backup

x402: the payment flow

 Client (agent)                                  Server
    │  GET /resource                                 │
    ├───────────────────────────────────────────────▶│
    │        402 PAYMENT_REQUIRED                     │
    │◀───────────────────────────────────────────────┤   + accepts: scheme, asset,
    │                                                 │     amount, payTo
    │  pay (e.g. stablecoin transfer)                 │
    ├───────────────────────────────────────────────▶│   verify settlement
    │  GET /resource + payment proof                  │
    │◀───────────────────────────────────────────────┤
    │        200 OK + resource                        │
  • Zero protocol fees · no accounts, no KYC, no API keys · server middleware: one line
  • Settlement: blockchain-agnostic (EVM, Solana), stablecoins first, extensible to traditional rails
Per la domanda "x402 vuol dire crypto?". Il punto del talk è il contratto HTTP-native, non la valuta; il settlement è agnostico. Se serve, il flusso qui spiega perché è una riga di middleware.
appendix A4 · backup

Security across the boundaries

  • A2A: auth declared in the Agent Card, enterprise-ready posture, transport security
  • MCP Apps: sandboxed iframes, no arbitrary page access
  • A2UI: client-owned component catalogue — the agent describes, never ships code
  • x402: settlement verified before the resource is served

Honest gap: cross-organization authorization models are the least standardized piece.

Per la domanda "e la security?". Chiudere sempre con la riga onesta: i modelli di autorizzazione cross-org sono il pezzo meno standardizzato di tutto lo stack.
