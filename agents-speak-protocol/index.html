history · part 1

Every revolution standardized how things talk

Before TCP/IP       → networks spoke dialects
Before HTTP         → every service invented its own wire format
Before REST         → SOAP was the only "enterprise" answer
Before WebSockets   → polling everywhere

Each time, entropy was reduced not by better applications, but by agreeing on how things connect.

⏱ min 2-4. Quattro righe, quattro epoche: non leggere le righe, raccontarle come un ritmo (chi era in azienda ai tempi di SOAP può confermare). Il punto non è la storia: è che l'entropia NON è stata ridotta da applicazioni migliori, ma da un accordo su come le cose si connettono. Land: "entropy was reduced by agreeing on how things connect".
history · part 2

History's rule

CORBA vs REST · SOAP vs JSON · WebSockets vs polling

Winners are rarely the most feature-rich.

The simplest protocol that reduces the most uncertainty wins.

⏱ min 4-5.5. Scegliere DUE guerre e raccontarle per bene, la terza solo citata: (1) SOAP vs JSON: vince il più semplice, non il più completo; (2) WebSockets vs polling: vince chi cambia il modello di comunicazione, non chi aggiunge feature. boundary 1 · the model

Open Responses

  • Early de facto: Chat Completions semantics (messages, roles, streaming, tool calls), adopted by clients, gateways, providers
  • Now: Responses API — typed items, semantic streaming events, state across turns
  • Open Responses: the same contract, open and multi-provider

Status: emerging

⏱ min 8.5-11. Parallelo storico da martellare: quando la semantica de facto di un vendor diventa la base del contratto neutro, come HTTP/1.1 de facto divenne standard IETF. Chat Completions ha vinto come dialetto comune; Responses è la generazione dopo (item tipati, eventi di streaming semantici, stato tra turni); Open Responses è la copia aperta multi-provider. Onestà sullo status: emerging, da pinnare, non da scommettere ancora.
boundary 2 · tools

MCP

  • JSON-RPC 2.0, three roles: host (LLM app) → client (in host) → server (capabilities)
  • Tools, resources and prompts through one connection
  • Extensions: MCP Apps (sandboxed interactive HTML), Skills over MCP (in development)

Status: de facto standard

⏱ min 11-15. Il confine più maturo, il "vincitore attuale". Perché ha vinto finora: semplice, SDK ovunque, e riduce il problema N×M (N agenti × M tool) a N+M. Spiegare i tre ruoli: l'host è l'app che ha il modello, il client sta nell'host, il server espone le capability. Attenzione onesta: MCP Apps e Skills-over-MCP sono estensioni, NON fanno parte del supporto base, verificare prima di dipendere. Questa è la slide in cui stare comodi: 4 minuti pieni.
boundary 3 · other agents

A2A

  • Agent Card for discovery · Messages · Tasks for stateful work · Artifacts for results
  • Streaming and push notifications for long-running work

Status: 1.0 stable

Key property: opaque execution — the remote agent keeps its model, tools and context private.

⏱ min 15-18. Passaggio di confine: non parliamo più di chiamare tool, ma di delegare lavoro a un altro partecipante autonomo. Percorrere il ciclo: scopri (Agent Card), incarica (Task), ricevi (Artifact), con streaming e push per il lungo periodo. Il punto chiave da anticipare (si spacca nella prossima slide): l'esecuzione è opaca per progetto, l'agente remoto non espone modello, tool né contesto.

Complement, don't compete: each does what it does best.

⏱ min 18-21.5. LA slide che l'abstract promette: architettura concreta, side by side. La distinzione da martellare: access to capabilities VS delegation to an autonomous participant. Nel diagramma: il nostro agente usa MCP per i SUOI tool, e A2A per delegare lavoro cross-org a un agente partner, che gira col suo stack e non espone nulla. Complementari, non competitivi. Esempio parlato (adattare al pubblico): un agente di supporto interno che gestisce i tool aziendali via MCP e delega a un agente partner la parte che richiede dati che non possediamo.
boundary 4 · users

Three names, one boundary

  • AG-UI: event stream between agent backend and user-facing app (run lifecycle, messages, tool calls, state); human-in-the-loop: pause for approval, resume later
  • A2UI: declarative UI from a client-owned component catalogue → native widgets, no arbitrary code from the agent
  • MCP Apps: interactive UI on the MCP side
  • The A2UI payload travels over AG-UI, A2A or any transport

Status: AG-UI: unratified draft A2UI: 0.9.1, 1.0 candidate

⏱ min 21.5-25. Tre nomi per un confine: mappa rapida di chi fa cosa, senza perdersi. AG-UI trasporta l'interazione (eventi), A2UI descrive l'interfaccia (dichiarativo), MCP Apps copre il lato MCP. Il punto di sicurezza del dichiarativo da dire esplicito: il client possiede il catalogo dei componenti, l'agente DESCRIVE, non impone codice. E human-in-the-loop (pausa per approvazione o credenziali, resume dopo) è il pattern che serve davvero in enterprise. Nomi nuovi, status da pinnare: dirlo senza scuse.
boundary 5 · knowledge & instructions

Knowledge rides the filesystem

  • AGENTS.md: repo convention, narrows as you descend
  • Agent Skills: a folder with SKILL.md + scripts and references; progressive disclosure (discover the name → load the instructions → execute)
  • Agent Plugins: one package, plugin.json + skills/ + mcp.json; vendor-neutral interoperability floor; spec 1.0.0, TSC from Amazon, Cursor, Microsoft, OpenAI, Vercel
  • OpenTelemetry GenAI: one trace across model calls, tools, agents — status Development
⏱ min 25-28. Ritmo da lista: il messaggio è che anche la conoscenza sta diventando un confine standardizzato. AGENTS.md è una convenzione, zero runtime, e funziona già oggi. Skills: progressive disclosure in tre stadi (nome → istruzioni → esecuzione), nata da Anthropic e ormai spec aperta. Plugins: il punto interessante per questo pubblico è l'interoperability floor (core portabile, il client tiene distribuzione e UX) e il TSC con cinque vendor pesanti: è il segnale a cui guardare. OTel GenAI una riga: Development, pinnare la versione.
boundary 6 · the ide — kept short on purpose

ACP

  • JSON-RPC between code editor and coding agent: init, sessions, prompt/progress, permissions, cancel
  • v1 stable v2 experimental
  • The LSP parallel — and where it stops: agents are stateful and act with authority
⏱ min 28-29. Breve DI PROPOSITO, e dirlo: è il confine che si collega meno agli altri, vive nel mondo IDE. Il parallelo giusto è LSP: un contratto invece di N integrazioni editor-specifiche. Ma dove il parallelo si ferma: LSP risponde a domande, l'agente tiene sessioni di stato e agisce con autorità sul codebase (permissions, cancel). Chi lo sta integrando e vuole il dettaglio: slide in appendice, ne parliamo dopo.
the newest boundary · payments

The boundary nobody used for 30 years

  • HTTP 402 "Payment Required": reserved in the protocol since 1996, never put to use
  • x402 revives it for agents: server answers 402 → client pays → retries with proof → 200
  • HTTP-native, no accounts, no API keys, one line of middleware
  • Blockchain-agnostic settlement (stablecoins first, extensible to traditional rails)

Status: production claims, adoption to be proved

⏱ min 29-31.5. La storia che chiude il cerchio: il protocollo aveva riservato un posto per i pagamenti trent'anni fa, gli agenti gli hanno dato un motivo per esistere. Le macchine non hanno carte di credito: il flusso request → 402 con le condizioni di pagamento → pay-and-retry è il contratto, non la valuta. Settlement blockchain-agnostic, stablecoin come caso primario ma estensibile a rails tradizionali (se esce la domanda crypto, questa è la risposta). Status onesto: production claims e foundation, ma adozione da dimostrare. Il flusso completo disegnato sta in appendice.

appendix A2 · backup

ACP, a closer look

  • JSON-RPC 2.0 between code editor and coding agent
  • Lifecycle: initialize → session/new → session/prompt (+ progress) → session/request_permission → session/cancel
  • Capability negotiation at init
  • v1 stable v2 experimental draft
  • The LSP parallel holds for the contract shape, not the semantics: LSP answers questions, the agent holds state and acts with authority on the codebase

appendix A3 · backup

x402: the payment flow

 Client (agent)                                  Server
    │  GET /resource                                 │
    ├───────────────────────────────────────────────▶│
    │        402 PAYMENT_REQUIRED                     │
    │◀───────────────────────────────────────────────┤   + accepts: scheme, asset,
    │                                                 │     amount, payTo
    │  pay (e.g. stablecoin transfer)                 │
    ├───────────────────────────────────────────────▶│   verify settlement
    │  GET /resource + payment proof                  │
    │◀───────────────────────────────────────────────┤
    │        200 OK + resource                        │
  • Zero protocol fees · no accounts, no KYC, no API keys · server middleware: one line
  • Settlement: blockchain-agnostic (EVM, Solana), stablecoins first, extensible to traditional rails
Per la domanda "x402 vuol dire crypto?". Il punto del talk è il contratto HTTP-native, non la valuta; il settlement è agnostico. Se serve, il flusso qui spiega perché è una riga di middleware.
appendix A4 · backup

Security across the boundaries

  • A2A: auth declared in the Agent Card, enterprise-ready posture, transport security
  • MCP Apps: sandboxed iframes, no arbitrary page access
  • A2UI: client-owned component catalogue — the agent describes, never ships code
  • x402: settlement verified before the resource is served

Honest gap: cross-organization authorization models are the least standardized piece.

Per la domanda "e la security?". Chiudere sempre con la riga onesta: i modelli di autorizzazione cross-org sono il pezzo meno standardizzato di tutto lo stack.
